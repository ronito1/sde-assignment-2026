Outcome Loop Controller

Watch what happened → decide → get permission → apply → check → record why. +15–31% leads concluded, 0 harmful changes.

0The brief

Problem

Formi runs outbound voice agents for insurers and lenders. Today a human sets each agent's welcome message, voice, caller ID, prompt and call hours once and rarely revisits them. Two KPIs matter and are never blended: pickup rate and engagement rate.

What had to be built

An always-on controller that, for every workflow, detects drift, experiments, proposes changes through client approval, applies and rolls back safely, and explains every change. It must survive crashes, respect supervisor edits and never bypass governance.

Tech used

  • Python 3
  • numpy
  • httpx
  • SQLite (WAL)
  • pytest
  • bash scripts

One process, one SQLite file, no new services. Talks to the simulator over HTTP only.

4Life of an experiment

  LAUNCH (needs approval)          70% control  ·  30% split across alternatives
     │
     ▼
  RUNNING ── every 6h: is an alternative clearly WORSE? ──▶ drop it (safe, automatic)
     │
     │ once a day: is one clearly BETTER (statistically, with ≥250 calls)?
     ▼
  PROMOTED (needs approval)        85% winner  ·  15% old control kept as a "holdout"
     │
     │ watch: is the winner fading?
     ▼
  DEMOTED to 50/50 (half the risk, and a fairer comparison)
     │
     ├── winner still clearly better ──▶ back to PROMOTED
     └── winner no better ─────────────▶ ROLLED BACK to the old control, winner banned

6How a change request travels

  PREPARED ──send──▶ PENDING ──▶ APPROVED ──apply──▶ APPLIED ✓
  (saved to disk         │           │
   BEFORE sending)       │           └─ config changed meanwhile ─▶ STALE → re-plan fresh
                         ├─▶ REJECTED → wait 12h before asking again
                         └─▶ EXPIRED  → treat as rejected, re-plan with fresh data

Saved before sending, so after a crash nothing is sent twice or forgotten.
